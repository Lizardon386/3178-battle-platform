## 0. 核心架构决策摘要

1. **质量属性排序：可维护性/解耦 > 会话可用性 > 一致性（单一权威）> 性能与成本。** 这是局域网小规模对战平台，不是高并发公网服务。按分布式系统那套上消息队列、注册中心、分片、多副本属于过度设计，**当前规模一律不引入**。
2. **权威单点保留，但换宿主**：从「平台进程内的 GameInstance」挪到「房主机上的独立 Game Authority 进程」。平台只做定序、鉴权与按座位路由，不解释 payload。这是 D2 的实质。
3. **平台仍持有会话共识（D1），但只持元数据与进程生命周期**：成员表、通用 ready、开始闸、票据、房主标记、revision、落盘；`startGame` 通过后才拉起 Game Authority。玩法状态、对局相位与视角裁剪归游戏。
4. **量级结论**：按 8 人房、每人每秒 2 动作、单条 200B 估算，单房间下行约 25.6 KB/s、连接数 9 条。单机 Node 进程绰绰有余，**性能不是瓶颈，不需要任何扩展机制**。
5. **最大风险不是性能，是两处**：① 视角私密性从平台保证退为游戏自律；② 网页客人的 `https`→`ws://` 混合内容问题未解决。这两条决定方案能不能落地，优先于任何选型。

## 1. 需求与约束

| 类别 | 内容 |
|---|---|
| 已知事实 | 局域网 / 邀请链接联机对战；房主制权威、无中央服务器；平台不做账号/好友/段位/匹配/目录服务器；Windows 优先；现有 `npm test` 233 例；color-duel v0.2.2 支持 2~8 人；现有限流 20 条/秒、突发 40 |
| 已知事实 | 房主单机一个进程、一个 Engine；落盘为 JSON 原子写且「内容没变就跳过」；掉线宽限 30 分钟 + `seatResume` |
| **缺失，需用户确认** | 预期规模（同时在线房间数、峰值并发连接、单房间人数上限）、团队技术栈（谁维护 TS / Rust / Kotlin 客户端）、预算与交付时间、合规（是否要 HTTPS 证书/域名、是否上架应用商店） |
| 显式假设 | 单房间 2–8 人；单机同时 1 个房；峰值 < 100 并发连接；以局域网为主、跨网靠邀请链接或隧道 |
| **假设变化的影响** | 若目标是公网 100 个并发房间（≈800 连接、下行 ≈2.5 MB/s、落盘 ≈1600 次/秒），需要会话分片、中继与独立鉴权服务，S1–S6 全部要重做，且「不买服务器」前提失效 |

本评审所有量级数字基于上述假设。**前提未确认前，不给性能或可用性承诺。**

### 质量属性排序依据

| 排序 | 属性 | 为什么排这里 |
|---|---|---|
| 1 | 可维护性 / 解耦 | 用户本次变更的唯一目标就是「游戏与平台不耦合」。契约漂移是长期最大成本 |
| 2 | 会话可用性 | 房主重启不能丢房、掉线要能坐回原位（猴测 Issue #4/#5 已证伪「不落盘」） |
| 3 | 一致性 | 单一权威必须保住，否则要做确定性帧同步，等于重写引擎 |
| 4 | 性能 / 成本 | 量级极小，无服务器、无中继，成本天然极低 |

## 2. 分层与边界

```text
┌─ 接入层 ──────────────────────────────────────────────┐
│ 桌面原生客人 / 网页客人 / 手机网页客人                  │
│ 传输：WebSocket(wss for web) · UDP 组播(仅发现)         │
└───────────────────────┬───────────────────────────────┘
                        │ 同步：hello/session*/game/notice
┌───────────────────────▼───────────────────────────────┐
│ 会话层  Session Service（平台进程，常驻）               │
│ 连接/心跳/重连 · 成员表+ready · 开始闸 · 票据 · 房主权限 │
│ 消息定序 · toSeat/toAll 投递 · 会话元数据落盘 · 进程拉起  │
│ 【不解释 payload，不裁剪视角，不在平台进程执行游戏代码】  │
└──────┬──────────────────────────────────┬─────────────┘
       │ 本地回环 IPC（推荐：长度前缀帧） │ 会话元数据
┌──────▼──────────────────────┐   ┌───────▼─────────────┐
│ 权威层  Game Authority       │   │ 基础设施：JSON 原子写│
│ 独立游戏进程（房主机）       │   │ 组播信标 · 隧道子进程│
│ 规则/状态机/机器人/存档      │   └──────────────────────┘
│ 自己决定给每个座位发什么      │
└──────┬──────────────────────┘
       │ 游戏 UI 由游戏自己渲染（平台不介入）
┌──────▼──────────────────────────────────────────────┐
│ 客户端层：平台壳（会话/成员/连接）+ 游戏 UI（独立）    │
└──────────────────────────────────────────────────────┘
```

**启动与移交边界**：未通过开始闸时不存在 Game Authority；通过后由 Session Service 拉起并交给它配置与成员 profile 快照。转交房主只转移权限，不把服务或权威迁到另一台机器。进程崩溃 / 退出只更新 `gameProcess`，不自动把会话解释成对局结束。

**同步/异步边界**：接入层↔会话层、会话层↔权威层是同步请求-响应加事件推送；组播发现、隧道拉起、落盘是异步；游戏 UI 与平台壳之间只有「打开游戏」这一个进程间动作，无状态同步。

## 3. 关键技术方案与选型

> 凡选型均给出「方案 / 优点 / 代价 / 适用条件」。**推荐项加粗**，并说明为什么不选其他。

### 3.1 平台 ↔ Game Authority 本地通道

| 方案 | 优点 | 代价 | 适用条件 |
|---|---|---|---|
| **回环 TCP + 长度前缀帧** | 跨语言、Windows/Linux 同一套、易抓包调试、超时与半包处理可控 | 要自己定帧格式、心跳与重连 | **当前场景：同机跨进程、语言可能不同** |
| Unix domain socket / Windows 命名管道 | 略快、不走网络栈 | 两套 API，跨端要分别实现 | 量级太小，收益不抵复杂度，不选 |
| stdio 管道 | 不用端口 | 双向多路复用难、进程管理脆弱 | 不选 |
| gRPC / protobuf RPC | 强类型、代码生成 | 引入运行时与构建链 | 当前 9 条连接，属过度设计；多语言 SDK 稳定后再评估 |

### 3.2 线协议编码

| 方案 | 优点 | 代价 | 适用条件 |
|---|---|---|---|
| **JSON(UTF-8) + JSON Schema 作为 spec** | 可读、跨语言零依赖、调试方便、与现有 wire 接近；Schema 仍是唯一字据，可生成多语言类型 | 体积比二进制大约 1.5–2× | **当前 3.2 KB/s 量级完全够，且可维护性优先** |
| MessagePack | 体积小 | 各语言都要带库 | 规模上来再换 |
| protobuf | schema 强、生成代码 | 需 `.proto` 工具链与版本管理 | 不选：现在引入会拖慢 S1 |
| 自定义二进制 | 极致体积 | 可维护性最差 | 不选 |

### 3.3 跨机传输与网页客人

| 方案 | 优点 | 代价 | 适用条件 |
|---|---|---|---|
| **双通道并存：原生客人走 ws/wss，网页客人走 wss（平台终结 TLS 或 cloudflared 隧道）** | 同时满足零安装与混合内容限制 | 需要证书/域名或隧道依赖；隧道域名每次启动仍会变 | **桌面原生 + 网页/手机网页客人并存** |
| 维持现状：`http://127.0.0.1` 页 + `ws://房主:3000` | 零改动 | `https` 页面连 `ws://` 被拦，手机/跨机浏览器不成立 | 仅本机调试 |
| 全量原生 TCP/WS 直连 | 原生端最简 | 网页客人没得用 | 不选，会丢掉零安装优势 |

**网页游戏的补充边界**：静态游戏包与管理 UI 必须分 origin；平台管理票据不下发到游戏页面，改用一次性 handoffCode 换受限 gameTicket。这样可以保留网页静态分发，又不让游戏脚本直接控制平台管理面。它不能替代 Game Authority 的动作校验。

**这一项是当前唯一未解决的工程问题**，无真机验证，需 S6 前定。

### 3.4 会话持久化

| 方案 | 优点 | 代价 | 适用条件 |
|---|---|---|---|
| **JSON 原子写（沿用现状）** | 已实现、已测、坏文件跳过、内容没变跳过 | 单文件；房间多了要分片 | **单机 1 房，直接沿用** |
| SQLite | 事务与查询 | 便携包要带原生二进制 | 房间数 > 100 时再评估 |
| 不落盘 | 最简单 | 房主重启丢房、真票据被拒 | 猴测 Issue #4/#5 已证伪，不选 |

### 3.5 平台壳的客户端形态

| 方案 | 优点 | 代价 | 适用条件 |
|---|---|---|---|
| **桌面房主端原生控件 + 网页客人保留现有页面** | 契合度最高，消掉浏览器那串税；两套实现共享一份交互契约 | 两套 UI 实现成本（用户已明确契合度优先、不看成本） | **目标形态** |
| 整个平台壳用 WebView 装本地页面 | 复用现有 UI，改动最小 | 把同源/沙箱/混合内容的税带进客户端 | 仅可作 S4 过渡 |
| 全网页 | 零安装 | 不能常驻、不能监听入站端口、不能弹防火墙授权 | 只适用于客人端 |

### 3.6 迁移期兼容 `[15:12 用户拍板：推倒重来]`

| 方案 | 优点 | 代价 | 适用条件 |
|---|---|---|---|
| **推倒重来，不设兼容适配器** | 一次做到位，无第二套契约，旧 ABI 彻底清干净 | color-duel v0.2.2 的 37 例测试、包、Release 与联调证据作废；平台 233 例中依赖旧契约的用例要重写；S2 失去旧游戏验收基准 | **用户已选** |
| 兼容适配器包旧 `GameModule` | 保住回归基线、旧游戏不改代码能跑 | 形成第二套契约，必须定退役日 | 已被用户否决 |

**架构缓解**：用「最小参考游戏」（按新协议实现建房→入席→准备→开始→一个动作→重连）替代兼容层，同时充当 S2 验收基准、SDK 示例与契约测试驱动。S1 先对 spec 生成的 mock 跑通，避免“不改运行时”与“真实全链路”同时写成验收。放在平台测试夹具里，不对外发布。

## 4. 容量与量级估算

**输入**（均来自本项目已有事实或第 1 节假设）：单房间 8 人；每人每秒 2 个动作（回合制实际上限远低于限流 20 条/秒）；单条动作 200 B；平台按 8 个座位广播；本机 UI 占 1 条连接；落盘每次约 2 KB。

| 指标 | 计算 | 结果 |
|---|---|---|
| 单房间上行 | 8 × 2 × 200 B | 3.2 KB/s |
| 单房间下行（广播 8 份） | 8 × 3.2 KB/s | 25.6 KB/s |
| 并发连接 | 8 客人 + 1 本机 UI | 9 条 |
| 落盘频率 | 每次可见状态变更 1 次，峰值 8×2 | ≤16 次/秒，约 32 KB/s |
| 现有限流余量 | 20 条/秒 vs 实际 2 条/秒 | 10× 余量 |

**结论**：这个量级下单机 Node 进程绰绰有余。不需要连接池、消息队列、限流中间件（现有限流已够）、分片、多副本、注册中心。落盘已有「内容没变就跳过」优化，SSD 上可忽略。

**假设变化的重算**：若公网 100 个并发房间 → 约 800 连接、下行约 2.5 MB/s、落盘约 1600 次/秒 → 需要会话分片与中继服务，第 2 节拓扑与 S1–S6 全要重做。**这不是性能承诺，是按给定假设的算术；假设未确认前不作为验收指标。**

## 5. 风险与对策（七维体检）

| 维度 | 风险 | 等级 | 缓解 | 可观测指标 |
|---|---|---|---|---|
| 可扩展性 | 双端两套实现导致交互契约漂移 | 中 | 协议 spec 唯一字据 + 生成类型 + 跨语言一致性测试 | spec 版本一致率、契约测试通过率 |
| 可用性 | 房主进程是单点 | **设计约束，不是缺陷** | 会话落盘恢复、30 分钟宽限、`seatResume` | 重启恢复成功率、票据 resume 成功率 |
| 一致性 | 视角裁剪归游戏，平台不再保证不泄露 | **高** | 平台提供 `toSeat`；SDK 必须给显式警告 + 裁剪示例 + 测试模板 | **平台不解释 payload，无法监控内容泄露，只能靠游戏侧测试** |
| 性能 | 低量级 | 低 | 无需措施 | 连接数、心跳 RTT、消息重发率 |
| 安全 | 房主不再执行第三方游戏代码（改善）；`wss` 混合内容未解（阻断网页客人） | **高** | S6 前定 TLS 终结或隧道方案并真机验证 | TLS 握手成功率、混合内容拦截数 |
| 可维护性 | 网页静态包若与管理 UI 同源，会把游戏脚本越权带进平台管理面 | **高** | 独立 origin + 受限 gameTicket + CSP + 越权契约测试 | 管理动作跨凭证拒绝率、CSP 拦截数 |
| 成本 | 无服务器、无中继，天然极低 | 低 | 若引入中继，前提「不买服务器」即失效，需重新拍板 | 隧道/证书依赖数 |

**监控补充**：`revision` 单调违例数、落盘失败次数、IPC 超时次数、`toSeat` 目标越界数。这些是平台能从元数据里看到的；payload 内容一律不可见。
