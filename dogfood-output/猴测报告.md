### Issue #1：连接还没就绪就发消息，抛未捕获的 `InvalidStateError`

| 字段 | 值 |
|---|---|
| **严重度** | 🟠 High |
| **类别** | Functional / Console |
| **位置** | [packages/client/src/connection.ts](file:///D:/agent_workspace/3178-battle-platform/packages/client/src/connection.ts) 的 `sendRaw` |

**现象（原文）**：
```
Uncaught InvalidStateError: Failed to execute 'send' on 'WebSocket': Still in CONNECTING state.
```

**复现步骤**：
1. 打开页面，连上任意房主（或点"重新连接"）；
2. 在连接还没到 OPEN 的那一瞬间点任意按钮（准备 / 发送聊天 / 建房 / 加入）。

**期望**：要么这一下不丢、连上后自动补发；要么明确告诉玩家"还在连"。
**实际**：`sendRaw` 只判了 `if (!this.socket)`，没判状态，于是直接对 CONNECTING 的 socket 调 `send()` → 抛异常。UI 表现为"点了没反应"，异常只在控制台里。

**根因**：`retryNow()`（"重新连接"按钮）会 `close()` 旧 socket 再 `open()` 新的；新 socket 立刻被赋给 `this.socket`，但此时还没到 OPEN。

**修法**：未就绪时把消息排进队列（上限 16 条），`open` 事件里在 `hello` 之后**按原顺序补发**；心跳 `ping` 明确不排队（过期的 ping 补发没意义）；主动关闭时清空队列。
**验证**：新增用例「没连上就发消息：不许抛 InvalidStateError，也不许静默丢掉，连上后按原顺序补发」——假 socket 故意照抄浏览器的抛异常行为，逼实现必须先判状态。修前该用例复现异常，修后通过。

### Issue #2：房主地址填了非法字符，`new WebSocket` 抛未捕获的 `SyntaxError`

| 字段 | 值 |
|---|---|
| **严重度** | 🟠 High |
| **类别** | Console / Functional |
| **位置** | [packages/client/src/endpoint.ts](file:///D:/agent_workspace/3178-battle-platform/packages/client/src/endpoint.ts) 的 `build()` |

**现象（原文）**：
```
Uncaught SyntaxError: Failed to construct 'WebSocket': The URL 'ws://<script>x</ws' is invalid.
```

**复现步骤**：
1. 在"房主地址"里填 `<script>x</script>`（或任何含空格、`<`、`>` 的串）；
2. 点"加入房间"。

**期望**：一句人话告诉玩家地址不能这么填。
**实际**：`parseHostAddress` 只看有没有冒号/端口，把整串当主机名拼成 `ws://<script>x</ws` 放行，异常在 `new WebSocket()` 处炸出，点"加入"的人只看到没反应。

**修法**：`build()` 里用 `new URL()` 自己校验一次（WHATWG 的 forbidden host code point 集合就是浏览器会抛的那批字符），不合法就返回 `BAD_HOST` + 中文提示；`btn-join` 本来就会把 `parsed.message` 显示出来，于是一句"这个地址连不成网址：填 IP 或域名，可以带端口（如 192.168.1.20:3000）"。
**验证**：新增用例覆盖 4 种非法输入 + 5 种正常写法不被误伤，并**如实记录一条边界**：引号 `"` 不在 URL 规范的禁列里，所以放行——它不会抛异常，只会连不上，走"连不上"那句提示。

### Issue #4：建房后 2 秒内被硬杀会丢房，朋友的邀请链接进来是"房间不存在"

| 字段 | 值 |
|---|---|
| **严重度** | 🟡 Medium |
| **类别** | Functional（持久性） |
| **位置** | [packages/server/src/engine.ts](file:///D:/agent_workspace/3178-battle-platform/packages/server/src/engine.ts) 的 `syncStore` + [packages/hostd/src/cli.ts](file:///D:/agent_workspace/3178-battle-platform/packages/hostd/src/cli.ts) 的同步间隔 |

**复现步骤**：
1. 起房主端，建房，拿到邀请链接；
2. **2 秒内**直接点控制台窗口的关闭叉（Windows 上那是 `TerminateProcess`，不走 SIGINT 收尾）；
3. 重开房主端，朋友用链接进来。

**期望**：房还在。
**实际**：落盘靠一个 2 秒的定时同步，所以这 2 秒内的房只存在于内存。实测（[tools/devtools/repro-persist.mjs](file:///D:/agent_workspace/3178-battle-platform/tools/devtools/repro-persist.mjs)）：

| 指标 | 修前 | 修后 |
|---|---|---|
| 建房成功 → 盘上出现 `room-<房号>.json` | **1912 ms** | **180 ms** |
| 加一个电脑位 → 盘上反映出来 | **1996 ms** | **252 ms** |

**修法**：`syncStore` 先比对上次落盘的内容原文，**没变的房直接跳过**，于是同步间隔从 2 秒压到 250 毫秒（跟心跳同频）而不产生空转写盘。
**验证**：新增用例「落盘跳过没变的房」——新建当场落 1 次、连调两次都是 0 次、座位一变就落。协议层猴测里那条 `seatResume(真票据) → error/NOROOM` 的时序（Issue #4 的表现）在修复后不再出现。

### Issue #5：加入房间后不到一个同步周期被硬杀，玩家拿真票据重连被拒

| 字段 | 值 |
|---|---|
| **严重度** | 🟡 Medium |
| **类别** | Functional（持久性 / 重连） |
| **位置** | [packages/server/src/engine.ts](file:///D:/agent_workspace/3178-battle-platform/packages/server/src/engine.ts) 的 `granted()` + [packages/hostd/src/cli.ts](file:///D:/agent_workspace/3178-battle-platform/packages/hostd/src/cli.ts) |

**这是 Issue #4 修完之后剩下的那截窗口**：落盘从 2 秒压到 250ms，但仍然是"先发票据、后（最多 250ms）落盘"。于是：

1. 玩家点邀请链接加入，客户端当场拿到票据（存在 localStorage）；
2. 250ms 内房主端被硬杀（点控制台 X = `TerminateProcess`，不走收尾）；
3. 盘上那个房还是"玩家还没加入"那一版；
4. 重启后房在、座位不在 → 玩家 `seatResume` 得到 `NOSEAT`，比 `NOROOM` 更难解释，因为他手里确实有一张真票据。

**复现**：`node tools/devtools/repro-resume.mjs 3533 0`（加入后 0ms 硬杀）。修前玩家重连失败，修后 `坐回去了（player，座位 s1ab959f63b）`。

**修法**：把不变式写成一句话——**票据离开进程之前，存着它摘要的那个座位必须已经在盘上**。引擎加一个 `onTicketIssued` 钩子，在唯一的票据发出点 `granted()` 里同步调用；宿主壳把它接到 `engine.syncStore(store)`。因为 `syncStore` 已经会跳过内容没变的房，这一刀只在"有人入座/重连坐回"时真的写盘，不会变成每条聊天都写一次。

**验证**：新增用例「票据离开进程前，座位必须已经在盘上」（**不手动调 syncStore**，只看拿到 `seatGranted` 的那一刻文件里有没有这个座位和它的 `secretHash`）；协议层两个偶发 seed 各重跑 5 次共 10 次全绿。

**现象**：展开列表后，鼠标移到第二行高亮不动，点也选不中。

**根因两条**：① 触发按钮上挂了 `blur → close`。真鼠标按在选项上时，焦点先从按钮移走 → `blur` 触发 → 列表被 `display:none` → mouseup 落在隐藏元素上，**浏览器根本不会再派发 click**，于是"点了没反应"。② 划过/键盘光标底色用 `--bp-raised`（`#1c1c28`），而弹层是 `#16161f` —— 差值太小，肉眼看不出光标在动。

**修法**：删掉 blur→close（收起只靠"点外面 / Esc / Tab"）；新增 `--bp-hover: #2a2a42`，并给"选中且划过"再加一档 `rgba(99,102,241,.28)`。`elementFromPoint` 已排除"被别的元素盖住"这一种可能。

**验证过程比结论更重要——我的检查脚本连续三版都抓不到它**：
1. 只发合成 `click` → 0 违规。合成派发**无条件送达**，绕过了"隐藏元素不收 click"这条真实规则。
2. 改成 mousedown 后调 `prev.blur()` → 仍 0 违规。**未聚焦的文档里 `.blur()` 不派发 blur 事件**，隐藏页正是这种状态。
3. 改成 `dispatchEvent(new Event('blur'))`，并把断言从"最后值对不对"改成机制层的"**mousedown 与 mouseup 之间列表不许变 hidden**" → 才终于抓到。

**反向验证**：把 `blur → close` 临时装回去重跑 → 猴测报 **16 条**；装回修复后 3 轮 × 5 用户 × 350 步 = 5250 次操作 **0 条**。以后写页内交互断言按这条来：合成 `click` 不等于真点击，隐藏页里 `.focus()/.blur()` 不一定派发事件。

**顺带修了一条测试脆弱点**：SIGINT 用例把端口写死成 3477，残留壳占口时子进程 `EADDRINUSE` 秒退，被报成"退出码不是 0"（看着像收尾坏了）→ 改成运行时 `freePort()`。连跑两次全量 **108/108**。

### Issue #9：地址簿点了没反应——下拉里留着一条共享存储里已经没了的地址

|---|---|
| **严重度** | 🟡 Medium |

**现象**：亮着的"用这条地址"点下去毫无动静，也不留一句话。

**真因（读代码就能证明，不是猜）**：`AddressBook.list()` 每次调用都从**同源共享存储**现读一遍。所以同一台机器开几个标签页时（这正是 iframe 猴测复现的场景），别的页"忘掉"某条之后，本页下拉里还留着那条旧选项 → `find()` 返回 `undefined` → **旧代码 `if (!entry) return;` 就地静默返回**。

**修法四处**：
1. 那条分支改成说话："这条地址已经不在簿子里了"，并当场重建下拉。
2. 「用这条地址」成功后也说话："已填入 … 和房号 …"（没记房号时明说"这条没记房号"）——填进去的值如果本来就等于原值，玩家看不出点没点上。

**实测（不是推理）**：修后 seed 424242 的帧 0 状态行里 `这条地址已经不在簿子里了` 真的出现过；seed 777 里 `已填入 http://127.0.0.1:3182，这条没记房号` 和 `已从地址簿忘掉 http://127.0.0.1:3182` 也都出现过——这几支不是死代码。

**没直接观察到的那半，如实记**：`btn-forget` 那一条我归因到第 4 点那个窗口（读代码得到的），改后不再报，但我**没能单独把它复现出来**。

### Issue #10：链路断开时房间命令被静默塞进待发队列——点了没反应，还会在意料之外的一刻生效

| 字段 | 值 |
|---|---|

**实测**：修后这句提示在 seed 424242（5 用户 × 200 步）的帧 0 状态行里出现过；同一配置 0 违规。

## 台子自己的 bug（这轮又被反向验证抓出来一个）

给上面两条布局问题加不变式时，我写了 `ig.querySelector('.btn')` 去取"同一行的按钮"——**但下拉触发器自己也带 `.btn` 类**（它是 `btn form-select bp-listbox-trigger`），于是拿到的是它自己，"等高"那条变成跟自己比，**永远不响**。装回 bug 跑第一轮果然只报出宽度那类（62 条，0 条等高），我才发现。改成 `filter(b => !b.closest('.bp-listbox'))` 之后：

| 状态 | 违规 |
|---|---|
| 把 `.input-group > .bp-listbox` 改回 `display:block`（装回 bug） | **128 条**：等高 60（`高 40.0 vs 46.1，底边差 -6.1px`）+ 占宽 60 + 其他 8 |
| 修好后 seed 424242 · 4 人 × 120 步 | **0 条** |
| 修好后 seed 777 · 5 人 × 200 步 | **0 条** |

**这就是反向验证的价值**：如果只跑"修好后 0 条"，这条写坏的断言会一直空转下去。另记：宽度那条我不用"小于 60px 就算窄"这种魔法数，而是算同一行的账（`本行宽 − 同行按钮宽 − 余量`），这样它对不同断点、不同按钮文案都成立。

## 备注

- **猴测器自己也修了三个 bug，如实记**（这些误报如果被当成平台 bug 报给你，比不测还糟）：
  ① 第一版把排程 `seatResume` 的 `setTimeout` 立刻 `clearTimeout` 掉了，等于重连后根本不发 resume，于是 6 个 seed 全报"有座位却被判无座位"——**假阳性**，且讽刺地正好复现了我刚修的客户端缺陷；改成"收到 welcome 立刻发"，与 app.ts 行为一致。
  ② 换房时没重置 `phase`，把"新房在 lobby"误判成"相位倒退"。
  ③ **归因错误**：`pendingIntent` 只有一个字段，而故意非法帧（假票据、非 JSON、缺字段）的回信到达时，后面好几发合法动作已经把它覆盖了——于是合法帧"背上"了非法帧招来的 `NOSEAT`。seed 707 一次报 10 条全是这个原因。改法：给未答复的非法发送记账（`pendingInvalid`），只有账上干净时才做这条断言，并且每步之间留 4ms 让回信落地。
  ④ **离席后仍记着旧座位**：`seatLeave` 之后再发合法帧，服务端回 `NOSEAT` 是**对的**，但台子以为还有座位，于是 seed 606 报 19 条。先试着"按快照座位表清座位"——不成立，因为离席后根本收不到那个房的快照了；改成与 `app.ts` 的 `leaveToLobby` 一致：发出 `seatLeave` 当场就把自己的座位信息清掉。
  四条都修完后，12 个 seed 才做到全绿。
  ⑤ **旧连接的回信会算到新连接头上**：`connect()` 换 socket 时没给消息处理器分代，重启前那发"假票据"的 `NOSEAT` 会晚到一步、正好落在真票据 resume 之后 → 误报"真票据被拒"。加了 `if (this.ws !== my) return` 的代际守卫。
  ⑥ **一个"用户"会同时挂多条活连接**：`connect()` 不关上一条，多条连接在抢同一个座位，服务端要走完"旧连接关闭 → 座位归属"的时序，台子却把它当一个人。改成先 `close()` 再建。
  ⑦ **seed 可复现是打折的**：台子与真实异步 I/O 赛跑，同一个 seed 两次能跑出不同结果（Issue #5 修前是 seed 303 五次里响一次）。所以本轮结论一律配"重跑 5~10 次"的计数，不靠单跑一次的红绿——⑤⑥ 修完 + 落盘钩子加上后，303/707 各 5 次共 10 次全绿，随后 12 个 seed 全绿。**这一步比 finding 本身更重要**：前 6 个 seed 那批"违规"如果直接报给你，就是 6 条假 bug。
- **可复现**：任何一条协议层违规都带 seed，照 `node tools/devtools/monkey.mjs --seed <N> --users 8 --steps 300 --restarts 3` 重跑即可。UI 层的 seed 在脚本参数里（`{seed, users, steps}`）。
- **测试总数**：`npm test` 由 99 条增至 **109** 条（Issue #1/#2/#4 各一条防回归，其余为落盘钩子、`resumeCodeFor`、`aiFillBlocker`、自绘下拉纯函数与样式守卫），全绿；接缝闸门与双档闸门均 exit 0。
